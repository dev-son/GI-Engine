# GI Engine 학습 기록

이 문서는 GI Engine을 만들면서 나눈 설명과 배운 내용을 집에서도 복습할 수 있도록 정리한 기록이다.
대화 원문을 그대로 옮기기보다, 나중에 다시 읽었을 때 이해하기 쉬운 형태로 계속 갱신한다.

## 최종 목표

단순히 DirectX로 게임 하나를 만드는 것이 목표가 아니다.

1. Windows와 C++의 동작 원리를 이해한다.
2. DirectX를 이용해 렌더링 시스템을 직접 만든다.
3. 작은 게임 엔진을 설계하고 구현한다.
4. 직접 만든 기능과 언리얼 엔진의 구조를 연결해서 이해한다.
5. 최종적으로 언리얼 엔진 소스 코드를 읽고 수정할 수 있는 엔진 개발자가 된다.

`GI Engine`이라는 이름은 인재원에서 완성하지 못했던 엔진 프로젝트에서 가져왔다.
이번에는 학습 과정을 기록하면서 끝까지 완성한다.

## 2026-11-12: 프로젝트 시작

### 학습 방식

처음부터 WinAPI와 DirectX의 모든 내부 구현을 외우지 않는다.

먼저 사용하기 쉬운 함수로 여러 가지를 만들어 보면서 재미와 감각을 익힌다.
그 뒤 이미 사용해 본 함수의 내부 구현을 한 겹씩 열어 분석하고 직접 다시 구현한다.

진행 순서:

```text
기능을 사용한다
→ 결과를 눈으로 확인한다
→ 내부가 어떻게 동작하는지 질문한다
→ 구현을 분석한다
→ 직접 다시 구현한다
```

현재는 `src/Game.cpp`만 수정한다. 다음 파일들은 나중에 분석한다.

- `src/GameAPI.cpp`: 입력과 그리기 함수의 실제 구현
- `src/main.cpp`: WinAPI 창, 메시지 처리, 게임 루프

### 언리얼 스타일 이름

학습용 코드와 언리얼 코드를 연결해서 기억할 수 있도록 이름을 맞췄다.

| GI Engine | 언리얼에서 연결되는 개념 | 역할 |
|---|---|---|
| `BeginPlay()` | `AActor::BeginPlay()` | 시작할 때 한 번 호출 |
| `Tick(float DeltaTime)` | `AActor::Tick()` | 매 프레임 상태 갱신 |
| `DrawHUD()` | `AHUD::DrawHUD()` | 매 프레임 화면 그리기 |
| `IsInputKeyDown()` | `APlayerController::IsInputKeyDown()` | 키 입력 상태 확인 |
| `FColor` | `FColor` | RGB 색상 표현 |

GI Engine이 언리얼 엔진과 완전히 같은 엔진은 아니다.
이름과 개념을 연결해 두되, 나중에는 실제 언리얼 구현과 차이점도 함께 공부한다.

## WinAPI 기초 개념

### `main`과 `wWinMain`

- `main`: 일반적인 콘솔 프로그램의 시작 함수
- `wWinMain`: Windows GUI 프로그램의 시작 함수

`wWinMain`이 자동으로 창을 만들어 주는 것은 아니다.
프로그램이 시작되는 진입점이며, 내부에서 창 생성 코드를 호출해야 한다.

### `WNDCLASS` / `WNDCLASSEX`

C++의 `class`와는 다른 개념이다.
Windows에 사용할 창의 종류를 등록하기 위한 설정 정보다.

주요 정보:

- 메시지를 처리할 함수
- 창 클래스 이름
- 마우스 커서
- 배경과 창 스타일
- 프로그램 인스턴스

흐름:

```text
WNDCLASSEX 작성
→ RegisterClassEx로 등록
→ CreateWindowEx로 실제 창 생성
```

### `HWND`

`HWND`는 handler가 아니라 **Handle to a Window**, 즉 창 핸들이다.

Windows가 관리하는 실제 창을 식별하기 위한 값이다.
C++ 객체 자체나 일반 포인터로 생각하면 안 된다.

### 메시지 처리

Windows 프로그램은 사용자의 입력과 창의 변화를 메시지로 받는다.

```text
GetMessage / PeekMessage
메시지 큐에서 메시지를 꺼낸다
        ↓
TranslateMessage
키보드 문자 입력 등에 필요한 변환을 한다
        ↓
DispatchMessage
해당 창의 WindowProc로 메시지를 전달한다
```

### X 버튼을 누르면

```text
X 버튼 클릭
→ WM_CLOSE 발생
→ 기본 처리에서 창 파괴
→ WM_DESTROY 발생
→ PostQuitMessage 호출
→ WM_QUIT이 메시지 큐에 들어감
→ 게임 루프 종료
→ 프로그램 종료
```

`PostQuitMessage`는 그 자리에서 프로그램을 강제 종료하는 함수가 아니다.
메시지 루프가 정상적으로 끝나도록 `WM_QUIT`을 넣는다.

## 2026-11-16: 키 입력과 부스터

### 입력 이벤트와 입력 상태

Windows는 키를 누른 순간 `WM_KEYDOWN`, 키를 뗀 순간 `WM_KEYUP` 메시지를 보낸다.
GI Engine은 이 메시지를 받아 키별 상태를 저장하고, 게임 코드는
`IsInputKeyDown`으로 현재 눌려 있는지를 매 프레임 확인한다.

```text
키보드 입력
→ WinAPI 메시지
→ 엔진이 키 상태 저장
→ Tick에서 입력 상태 확인
→ 위치 변경
→ DrawHUD에서 결과 출력
```

캐릭터 이동은 키를 누르는 동안 계속 실행돼야 하므로 `눌린 순간`이 아니라
`현재 눌려 있는 상태`를 사용한다.

### 스페이스바 부스터 구현

- 평상시에는 기본 이동 속도를 사용한다.
- 스페이스바를 누르는 동안 기본 속도의 두 배로 이동한다.
- 부스터 중에는 플레이어를 빨간색으로 표시한다.

처음 구현에서는 부스터 상태와 평상시 상태에 방향키 이동 코드를 각각 작성했다.
기능은 정확히 동작했지만 이동 코드가 두 번 반복됐다.

두 경우를 비교하면 달라지는 것은 이동 방식이 아니라 `속도 값`뿐이다.
따라서 현재 속도를 먼저 결정한 뒤 공통 이동 코드를 한 번만 실행하도록 개선했다.

```text
현재 속도 = 기본 속도
→ 스페이스바가 눌렸으면 부스터 배율 적용
→ 결정된 속도로 공통 이동 처리
```

그리기도 같은 원리로 정리했다.

```text
플레이어 색상 = 기본 색상
→ 스페이스바가 눌렸으면 빨간색
→ 결정된 색상으로 DrawRect 한 번 호출
```

### 이번에 배운 설계 관점

- 조건마다 코드를 복사하기 전에 실제로 달라지는 값이 무엇인지 찾는다.
- 조건문에서는 달라지는 값을 결정하고 공통 동작은 한 번만 실행한다.
- `CurrentSpeed`처럼 한 프레임에서만 필요한 값은 `Tick`의 지역변수로 둔다.
- `MoveSpeed`와 `BoostMultiplier`처럼 고정된 설정값은 `constexpr`로 표현할 수 있다.
- 처음에는 명확하게 작동하도록 작성하고, 동작을 확인한 뒤 중복을 제거해도 된다.

`const`는 실행 중 값이 정해질 수 있지만 한 번 정한 뒤 바꾸지 않는 값이고,
`constexpr`은 컴파일할 때부터 값이 확정되는 상수다.

### 다음 과제: 화면 경계 처리

화면 크기는 800×600이고 플레이어 크기는 50이다.
플레이어 좌표는 사각형의 왼쪽 위이므로 허용 범위는 다음과 같다.

```text
0 ≤ PlayerX ≤ 800 - PlayerSize
0 ≤ PlayerY ≤ 600 - PlayerSize
```

방향키 이동이 끝난 뒤 플레이어가 범위를 벗어났는지 검사하고 위치를 보정한다.

### 화면 경계 처리 완료

처음에는 이동하기 전에 경계를 검사했다. 예를 들어 X가 749인 상태에서 한 프레임에
4만큼 오른쪽으로 이동하면 검사 시점에는 정상 범위이므로 통과하고, 이동 후 753이 된다.
따라서 이동 결과가 한 프레임 동안 화면 밖에 나타날 수 있었다.

실행 순서를 다음과 같이 수정했다.

```text
속도 결정
→ 입력에 따라 위치 이동
→ 이동 결과의 경계 검사
→ 허용 범위로 위치 보정
```

왼쪽과 오른쪽은 보정할 값이 다르므로 `||`로 하나의 조건에 묶지 않고 각각 검사했다.
오른쪽과 아래쪽에서는 사각형의 왼쪽 위 좌표뿐 아니라 `PlayerSize`도 고려했다.

```text
PlayerX 최대 = ScreenWidth - PlayerSize
PlayerY 최대 = ScreenHeight - PlayerSize
```

`ScreenWidth`와 `ScreenHeight`는 실행 중 변하지 않고 컴파일할 때 값이 확정되므로
`constexpr` 상수로 표현했다. `MaxX`라는 이름보다 화면 크기라는 실제 의미도 명확하다.

### GI Engine 전용 `DrawCircle` 추가

공을 사각형으로 대신 그리지 않고 게임 코드에서 의도를 직접 표현할 수 있도록
`DrawCircle` API를 추가했다.

공개 입력값:

- 색상
- 원의 중심 X와 Y
- 반지름

게임 코드는 원을 그려 달라고 요청하고, 엔진 내부의 `GameAPI.cpp`가 현재 렌더링 기술인
GDI로 그린다. 내부에서는 중심과 반지름을 다음 사각 영역으로 변환한다.

```text
왼쪽   = CenterX - Radius
위쪽   = CenterY - Radius
오른쪽 = CenterX + Radius
아래쪽 = CenterY + Radius
```

이 구조 덕분에 나중에 GDI를 DirectX로 교체할 때 게임 코드가 렌더링 세부사항을
직접 알 필요가 없다. `DrawCircle`은 언리얼의 실제 동일 API가 아니라 GI Engine 전용
2D API이며, 게임 코드와 렌더러를 분리하는 설계 원리를 배우기 위한 것이다.

### 다음 과제: 자동으로 움직이는 공

`Game.cpp`에 공의 중심 위치, 반지름, X/Y 방향 속도를 만들고 매 프레임 다음 원리로 이동한다.

```text
새 X = 기존 X + X 속도 × DeltaTime
새 Y = 기존 Y + Y 속도 × DeltaTime
```

공의 위치와 속도는 실행 중 변해야 하고, 반지름은 현재 실습에서 고정할 수 있다.
우선 화면 밖으로 사라질 때까지 자동 이동시키고, 다음 단계에서 벽에 튕기게 만든다.
